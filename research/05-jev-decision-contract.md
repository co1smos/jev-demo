# Strict once-per-minute JEV decision contract

Status: proposed research design, not investment advice and not a claim of production readiness.

## Recommendation

Use one immutable `DecisionPacket` per account and minute, with:

1. a deterministic, fully validated input envelope;
2. one batched JEV request containing only narrow semantic judgments;
3. a deterministic reducer that either emits one bounded action or abstains; and
4. a separate execution service that revalidates current broker state before submitting an order.

This is the smallest/deepest shape because it gives JEV one job—score bounded semantic evidence—while one code-owned contract handles time, arithmetic, risk, idempotency, validation, persistence, and side effects. TypeSafe explicitly says code should own control flow, deterministic rules, and side effects, while System One should answer narrow typed questions and code should compose the results.[1] JEV 1.13 is documented as weak at arithmetic, numeric precision, and date/time comparison, so none of those may be delegated to it.[2]

A once-per-minute cadence is an application scheduler decision, not a verified JEV feature. This contract is minute-frequency portfolio automation, not high-frequency trading in the market-microstructure sense.

## Verified JEV boundary

Verified upstream behavior used here:

- The HTTP interface is `state + named typed questions -> named typed answers`; the documented primitives are `Choice`, `Score`, and `Noul`.[3]
- `Choice` returns a selected option, all option probabilities, and confidence; `Noul` returns only the probability that the proposition is true.[3][4]
- Questions in one request are evaluated independently and in parallel against the same state. Code is expected to decide which answers matter and compose them.[1][5]
- A `Choice` may contain at most 255 options, and upstream recommends an explicit `other`/`none of the above` option where coverage may be incomplete.[3][6]
- Typed/schema-conforming output does not establish that a judgment is correct. Confidence is derived from the returned distribution and thresholds must be evaluated on domain data and matched to action risk.[7]
- JEV 1.13 accepts text only, represented as a string, JSON object, or array of text values; documented limits are 64k tokens for a request and 32k for state plus the longest question.[8]
- Model aliases can move. The response reports the versioned model that answered; upstream recommends pinning a version when thresholds were tuned against it.[8]
- Documented service errors include `401`, `422`, `429`, and `529`; `429`/`529` should use exponential backoff, and official SDK defaults do so.[3]
- JEV 1.13 documentation warns about literal reading, irrelevant large state, adversarial content, indirection, numeric work, date/time work, and generation.[2]

Not assumed because primary sources do not verify it:

- broker connectivity, market-data access, order submission, cancellation, fills, or exchange timestamps;
- exactly-once processing or an API idempotency key;
- transactionality, durable storage, replay logs, scheduling, or a once-per-minute trigger;
- deterministic equality of repeated live responses as an execution guarantee;
- a prose rationale generated by JEV;
- suitability, accuracy, calibration, or profitability for this trading domain;
- permission for JEV to override a risk rule or directly cause a side effect.

## Ownership split

| Deterministic code owns | JEV may own |
|---|---|
| UTC schedule and minute bucket | Narrow semantic judgment over supplied, normalized evidence |
| source timestamps, market calendar, session phase, bar closure and data-window completeness | Per-candidate thesis support as a `Noul` |
| broker cash, buying power, settled cash, positions, open orders, fills and reconciliation | Per-candidate contradiction/red-flag likelihood as a `Noul` |
| candidate universe construction and stable symbol ordering | Optional `Choice` among already eligible candidates plus `ABSTAIN` |
| indicators, returns, volatility, rankings, prices, quantity, notional, fees, P&L and every other calculation | Optional semantic regime/evidence labels from closed options |
| allowlists, deny rules, exposure limits, concentration, turnover, loss/drawdown limits, cooldowns and kill switches | No arithmetic, timing, sizing, policy, or execution |
| allowed-action derivation, idempotency, schema checks, confidence gates and fallback | Typed probabilities only |
| order intent creation, pre-trade revalidation, broker call, result verification and audit persistence | No side effects |

## Recommended interface: one immutable packet, atomic JEV signals, code-owned reducer

### Input contract

Canonical JSON is serialized with sorted keys and normalized numeric strings before hashing. Required fields:

```json
{
  "contract_version": "jev-minute-decision/v1",
  "decision_id": "<account_id>:<strategy_id>:<minute_utc>",
  "minute_utc": "YYYY-MM-DDTHH:MM:00Z",
  "scheduled_at_utc": "...",
  "assembled_at_utc": "...",
  "deadline_utc": "minute_utc + configured budget",
  "model_id": "jev-<pinned-version>",
  "strategy_version": "immutable identifier",
  "risk_version": "immutable identifier",
  "account": {
    "account_id": "opaque stable id",
    "broker_snapshot_id": "...",
    "broker_as_of_utc": "...",
    "currency": "USD",
    "cash": "decimal string",
    "settled_cash": "decimal string",
    "buying_power": "decimal string"
  },
  "positions": [
    {
      "symbol": "canonical symbol",
      "quantity": "decimal string",
      "market_value": "decimal string",
      "average_cost": "decimal string",
      "unrealized_pnl": "decimal string"
    }
  ],
  "open_orders": [
    {"broker_order_id": "...", "symbol": "...", "side": "BUY|SELL", "quantity": "decimal string", "status": "..."}
  ],
  "data_window": {
    "source": "named feed",
    "window_start_utc": "...",
    "window_end_utc": "...",
    "latest_complete_bar_end_utc": "...",
    "expected_bar_count": 0,
    "observed_bar_count": 0,
    "source_snapshot_id": "...",
    "source_digest": "sha256:..."
  },
  "candidates": [
    {
      "symbol": "canonical symbol",
      "rank": 1,
      "eligible": true,
      "features": {"code_computed_named_feature": "decimal|string|boolean"},
      "evidence": ["short provenance-tagged text fact"]
    }
  ],
  "constraints": {
    "allowed_actions": ["ABSTAIN", "HOLD", "BUY", "SELL"],
    "eligible_symbols": ["..."],
    "max_one_action": true,
    "max_order_notional": "decimal string",
    "max_position_notional": "decimal string",
    "max_gross_exposure": "decimal string",
    "max_daily_loss": "decimal string",
    "min_cash_reserve": "decimal string",
    "whole_shares_only": true,
    "market_orders_allowed": false
  },
  "input_digest": "sha256:<canonical packet excluding this field>"
}
```

Strict rules:

- All timestamps are RFC 3339 UTC. `minute_utc` is floored by code; JEV never parses or compares it.
- `data_window.window_end_utc <= minute_utc`; only completed bars are admitted. Code rejects stale, future, duplicated, gapped, mixed-frequency, or post-deadline snapshots.
- The broker snapshot and market-data snapshot must be within configured freshness bounds. Those numeric bounds are strategy configuration selected and tested outside JEV; this report does not invent values.
- Candidate symbols come only from deterministic universe/filter/ranking code. Candidates are deduplicated, canonically sorted, capped before inference, and must all be tradable and present in `eligible_symbols`.
- Raw news, social posts, filings, or other untrusted text is not passed through indiscriminately. It must be provenance-tagged, size-capped, and treated as data; upstream warns adversarial state can move JEV answers.[2]
- `constraints.allowed_actions` is derived by code from current account, positions, open orders, session state, and risk policy. JEV cannot add an action or symbol.
- The actual JEV state should omit fields irrelevant to its semantic questions. Full audit input remains stored locally, while JEV receives a compact projection; upstream says irrelevant large state reduces accuracy.[2]

### One batched JEV request

Do not ask “what trade should I make?” It combines policy, arithmetic, timing, and several judgments. Ask independent atomic questions in one request, for example:

- For each candidate `S`, `thesis_supported.S` (`Noul`): “Does the supplied evidence for `candidates[i]` support the strategy’s named semantic thesis, under the explicit true/false criteria?”
- For each candidate `S`, `material_contradiction.S` (`Noul`): “Does the supplied evidence contain a material contradiction to that thesis?”
- Optional `selected_candidate` (`Choice`): eligible symbols plus `ABSTAIN`, with criteria that compare only the semantic evidence. Include `ABSTAIN` because no symbol may fit.[6]
- Optional `evidence_quality.S` (`Choice`): `SUFFICIENT`, `MIXED`, `INSUFFICIENT`; use its full probability distribution and confidence.

Do not ask JEV to calculate indicators, decide whether timestamps are within the window, size a trade, compare dollars to limits, infer missing data, or produce rationale text. Questions are version-controlled artifacts. Their exact instructions and criteria, question IDs, candidate-to-index mapping, and request digest are stored in the audit record.

### Deterministic reducer and output contract

The reducer consumes the validated input and raw JEV response and emits exactly one `DecisionRecord`:

```json
{
  "contract_version": "jev-minute-decision/v1",
  "decision_id": "same as input",
  "status": "ACTIONABLE|ABSTAINED|FALLBACK",
  "action": "ABSTAIN|HOLD|BUY|SELL",
  "symbol": null,
  "quantity": null,
  "order_type": null,
  "limit_price": null,
  "reason_codes": ["..."],
  "rationale": {
    "template_id": "deterministic template/version",
    "facts": ["machine-selected references to stored inputs and answers"]
  },
  "jev": {
    "requested_model": "pinned id",
    "returned_model": "versioned id",
    "request_digest": "sha256:...",
    "raw_response_digest": "sha256:...",
    "answers": {},
    "threshold_policy_version": "..."
  },
  "validation": {
    "input_valid": true,
    "response_valid": true,
    "risk_valid": true,
    "fresh_at_reduction": true
  },
  "created_at_utc": "..."
}
```

Reduction order is fixed and fail-closed:

1. If an existing final record for `decision_id` exists, return it without calling JEV or submitting another order.
2. Validate the packet, freshness, market/session state, candidate coverage, digests, and deterministic constraints. Any failure -> `ABSTAIN` with a specific code.
3. Call the pinned JEV model once before `deadline_utc`. Validate HTTP status, schema, exact answer-key set, answer types, selected options, finite ranges `[0,1]`, probability sums within a declared tolerance, and returned model ID.
4. Apply versioned thresholds learned from a held-out, time-separated evaluation set. Thresholds are not copied from documentation examples. A candidate is usable only if every required atomic gate passes; missing, borderline, conflicting, `ABSTAIN`, or low-confidence evidence produces abstention.
5. Apply deterministic strategy and risk rules again. Select at most one action from `allowed_actions`; compute side, quantity, price bounds, and notional solely in code.
6. Render rationale from a fixed template using only stored facts and raw answer values. JEV is not a text generator.[2]
7. Atomically persist the final decision before handing an order intent to execution.
8. Immediately before broker submission, execution reloads cash, positions, open orders, market status, quote/price guard, and kill switches. If state changed or the intent no longer passes, do not submit; append a superseding `EXECUTION_ABORTED` event.
9. Submit with a broker-supported client/order id derived from `decision_id` if the broker actually documents that feature. Otherwise use a local outbox plus reconciliation; never assume broker idempotency.
10. Read back broker state/order status and append the observed result. A network timeout is `UNKNOWN`, not permission to resubmit blindly.

### Confidence, rationale, and abstention

- Store raw probabilities and JEV confidence; do not reduce the audit trail to one opaque score.
- A `Noul` has no separate confidence field: closeness to `0.5` expresses uncertainty.[4]
- `Choice` confidence measures distribution concentration, not truth, permission, expected return, or risk compliance.[7]
- Use action-specific gates. However, because any live order is consequential, initial deployment should only emit `HOLD/ABSTAIN` in shadow mode until target-domain calibration, stability, and end-to-end execution controls pass predefined tests.
- Rationale is deterministic: reason codes plus references such as `CANDIDATE_NOT_SELECTED`, `THESIS_BELOW_THRESHOLD`, `CONTRADICTION_ABOVE_LIMIT`, `LOW_CHOICE_CONFIDENCE`, `DATA_STALE`, `RISK_LIMIT`, or `JEV_UNAVAILABLE`. Do not claim chain-of-thought or model-generated reasoning.
- `ABSTAIN` is a first-class successful output, not an exception. No valid, timely, high-confidence, risk-compliant action means `ABSTAIN`.

### Idempotency and auditability

Use two related keys:

- `decision_id = account_id + strategy_id + minute_utc`: one logical decision per account/strategy/minute.
- `input_digest`: exact immutable contents used for that decision.

The persistent state machine is append-only:

`ASSEMBLED -> VALIDATED -> JEV_REQUESTED -> JEV_RECEIVED -> DECIDED -> ORDER_INTENT_RECORDED -> SUBMISSION_UNKNOWN|SUBMITTED|EXECUTION_ABORTED -> RECONCILED`

Enforce a uniqueness constraint on `decision_id` for the final decision and on `(decision_id, event_type, attempt)` for events. A duplicate request with the same digest replays the stored result. The same `decision_id` with a different digest is a hard conflict and abstains; it is never silently recomputed. Store canonical input, compact JEV projection, question definitions, request/response bodies or encrypted object references, hashes, timestamps, model IDs, usage, validation results, reducer/risk versions, order intent, broker acknowledgements, and reconciliation observations.

This idempotency is application-owned. The verified JEV API documents request evaluation and common error handling, but the reviewed primary sources do not document an exactly-once or idempotency-key facility.[3]

### Validation and fallback

Fallback is deterministic and non-trading:

- Invalid/missing/stale data, no candidates, policy violation, JEV timeout, `401`, `422`, exhausted `429`/`529` retry budget, malformed response, unexpected model version, missed deadline, threshold failure, or state drift -> `ABSTAIN`.
- Permit only retries that fit inside the same minute’s deadline and cannot create a second decision record. Backoff behavior must be bounded by the scheduler deadline even though upstream recommends exponential backoff for `429`/`529`.[3]
- Do not fall back to `jev-latest`, a different model, an LLM, cached prior-minute advice, or a deterministic trade signal unless that alternative is separately specified, versioned, evaluated, and authorized. The safe default is no new order.
- If JEV is unavailable, deterministic code may still perform housekeeping that cannot increase exposure, such as observing/reconciling broker state or enforcing an independently specified emergency risk control. That is outside the JEV decision.

## Interface-shape comparison

| Shape | Description | Audit/correctness | Size/depth | Verdict |
|---|---|---|---|---|
| A. Monolithic `Choice` | One request asks `BUY_S`, `SELL_S`, `HOLD`, `ABSTAIN` over all candidates; code executes the winner after risk checks. | Small wire format, but it hides thesis, contradiction, uncertainty, and direction inside one broad judgment. Candidate/action cross-products dilute options and encourage JEV to perform unsupported multi-factor reasoning. | Small surface, shallow module. | Reject. Typed output is not enough; the decision boundary is not inspectable. |
| B. Atomic signals + deterministic reducer | One immutable packet; batched per-candidate `Noul`/small `Choice` judgments; code applies thresholds, strategy, risk, sizing, idempotency, execution, and rationale. | Best separation, replayability, threshold tuning, failure attribution, and fail-closed behavior. Matches upstream guidance to decompose and compose in code.[1] | One deep module with a narrow seam: packet in, one action/abstention out. | Recommend. |
| C. Two-stage JEV cascade | First request filters/ranks; second request chooses among survivors or verifies the proposed action. | Can reduce later state and add a distinct verification judgment, but creates another network dependency and permits stage-one output to shape stage two. Harder deadline, replay, and failure semantics. | Larger and more coupled. | Defer until measured evidence shows shape B cannot meet candidate-count or accuracy needs. |

## Acceptance gates before any live orders

1. Schema/property tests prove malformed timestamps, decimals, symbols, windows, candidate mappings, probabilities, and model IDs fail closed.
2. Replay tests prove the same stored packet and response always produce the same decision record and rationale.
3. Concurrency tests prove duplicate schedulers, retries, crashes, and unknown broker outcomes cannot create two order intents for one `decision_id`.
4. Historical walk-forward tests include fees/slippage assumptions in code and compare against a deterministic no-JEV baseline; no leakage from future bars or revised data is allowed.
5. A labeled, time-separated set measures each JEV question’s calibration, threshold accuracy, abstention rate, candidate coverage, model-version sensitivity, and adversarial-text behavior. Upstream says thresholds depend on the domain and consequences.[7]
6. Shadow mode runs the exact live ingestion and decision path with order submission disabled; reconcile every minute and investigate missing or conflicting records.
7. Paper trading then verifies broker adapters, fractional/whole-share behavior, market hours, partial fills, cancellations, rejects, reconnects, and `UNKNOWN` submission recovery.
8. Live rollout, if separately approved, begins with hard code-owned exposure caps and a kill switch. Model/version/question/threshold changes require a new version and repeated gates.

## Conclusion

Adopt shape B: a single immutable per-minute packet, one batched set of atomic JEV judgments, and a deterministic reducer/executor. It is smaller than a staged agent or cascade and deeper than a monolithic action classifier: one auditable seam contains the full decision lifecycle, while JEV remains a replaceable bounded judgment provider. The critical safety property is simple: JEV may supply probabilities about supplied evidence; only deterministic code may decide whether an action is valid, calculate it, persist it, or execute it.
